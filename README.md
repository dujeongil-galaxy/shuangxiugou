## 🍴 Fork 与二次开发

**准备 Fork 或基于本项目改数据？请先读 [`FORK_GUIDE.md`](FORK_GUIDE.md)。**

### ⚠️ 动手前必读：[`PITFALLS.md`](PITFALLS.md)（踩坑与失效模式报告）

那份文档记录本项目**真实发生过**的故障 —— 每一条都对应一次返工，
其中多条是「**改完校验全绿、页面上完全没变化**」的静默失效。

**本文档最大的价值：让你别重走一遍已经踩过的坑。**

五类最容易中招的地方：

| 类别 | 一句话概括 |
|---|---|
| **静默失效** | 语法对、校验绿、功能不工作。用文案当选择器、CSS 重复选择器、`:has()` 真机不生效、`existsSync(URL)` 静默返回 false、`202 Accepted` 但提交了 0 条、React 复用 DOM 节点导致注入内容跑到别的卡上 |
| **改了不生效** | 数据分散在两处、根目录有非部署副本、忘了递增 `?v=N`、CSS 引用顺序颠倒、GitHub issue 模板格式选错 |
| **校验脚本自身的坑** | 正则命中注释造成误报、检查范围窄于风险面、用位置判断找错基准点、报错信息说反了 |
| **布局计算** | 算宽度只算了单项没算总量、`flex` 三值语义、容器固定高是隐藏坑、响应式要按区间验 |
| **数据核实** | 「439 家企业」实际 92 条（占位符）、8 个「同类项目」其实是同一上游克隆、对方回「Done」但没真的挂 |

**如果你只读一节，读「一、静默失效」和文末的「七、改动前检查清单」。**

### 六件最容易踩坑的事

1. **数据合规优先**：本项目内容是对具名企业的劳动评价，MIT协议只管代码不管内容合法性。改数据必须同步更新证据说明，**不要删除站内免责声明**。
2. **改错位置不生效**：53 张内置卡数据在 `assets/index-YthXZ9eP.js`，128 张自定义卡在 `index.html`；根目录另有一份同名 js 是**非部署副本**，改它无效；改 bundle 后须递增 `?v=N` 防缓存。
3. **不要试图构建后部署**：`app/` 源码与线上产物是两套数据，重建会覆盖现有站点。2026-11-13 起 Next 应用栈（`next` / `react` / `react-dom` / `framer-motion` / `tailwindcss-animate`）连同 `dev`/`build`/`start`/`lint`/`check-types` 脚本已整体移除（`npm audit` 从 8 项漏洞归零），仓库里**已不再提供 `npm run build`**，`app/` 仅作历史留存。
4. **改完跑一次校验**：`npm run verify`（零依赖，不需要 `npm install`）。它会检查卡片数量、logo 与资源路径、noscript 是否同步、文档数字口径、提交号真实性、h2/h3 双查、换行符锁定等，有问题直接 `exit 1`。**这是唯一能发现「静默失效」的手段** —— 本站的补丁脚本失败时页面上看不出任何异常。
5. **加检查之后必须注入故障验证**：`verify.mjs` 里的检查自己踩过很多坑（见 `PITFALLS.md` 第三节）。**没经过「故意注入故障、确认能抓到」的检查，不算加了检查** —— 它可能范围太窄、可能恒真、可能只是摆设。
6. **往 React 渲染的 DOM 里手动插节点，必须假设它会被移位**：

   本站是「React 渲染后用 `index.html` 里的脚本抓 DOM 再改写」的事后打补丁架构。
   **React 重渲染时按位置复用 DOM 节点** —— 卡片被搜索过滤掉后，React 会把那个节点
   原地改写成另一张卡（只更新文本，不重建节点）。而你手动插入的额外子节点
   **React 不认识，文本更新不会清掉它**。

   真实故障：搜索框输入 `HU`，苹果卡消失，但苹果专属的「富士康补充说明」
   留在了华为卡里（`PITFALLS.md` 1.10）；以及搜索无匹配词（如「啊」）时，
   说明框孤零零挂在空搜索面板里（同节 1.10 第二变体）。

   ⚠️ **反向的坑（2026-10-22 修复）**：修 bug ③ 时加的「搜索框一有输入就无条件
   摘除说明框」这条闸，把「说明框只属浏览态」当成了硬规则 —— 结果搜索**命中苹果卡**
   的词（如搜「苹果」）时，苹果卡明明在结果列表里，说明框却被摘掉了（站长截图）。
   **判据必须是「目标卡片在不在当前可见列表」，而不是「有没有在搜索」**。
   「过滤态就一律隐藏」和「过滤态就一律显示」同样是错的。

   写这类补丁必须遵守三条：

   ```js
   // ① 先清后插，不能「已存在就跳过」——那样错位后永远无法纠正
   var existing = document.getElementById('my-note');
   if (existing && existing.parentNode) existing.parentNode.removeChild(existing);

   // ② 目标卡片不在当前列表时，直接不插入
   var target = /* 在当前可见卡片里找 */;
   if (!target) return;

   // ③ 目标卡片「在 DOM 但整棵子树被隐藏」时同样摘除
   //   （沿祖先链查 inline display:none，覆盖筛选的隐藏方式），
   //   且同步清理（不等防抖，防残留一帧）——但只在目标卡片确实不可见时清理，
   //   搜索命中目标卡片时必须保留，否则会误伤正常场景。
   ```

   并且**搜索输入 / 品类评级切换后都要重新调用** —— 这两个操作都会改变卡片列表。
   识别目标卡片用**标题**（卡内 h2/h3）而不是全文子串：华为卡的同品类替代
   推荐区也含「Apple (苹果中国)」，全文匹配会把说明框误插进华为卡。

   改完用 `npm run test:apple-note` / `npm run test:starbucks-note` 验收：
   它用无头浏览器跑真实 React 搜索，覆盖「搜中目标卡保留 / 无匹配词摘除 /
   清空复原 / 搜别家不泄漏 / 子树被隐藏时摘除」五类场景
   （测React 受控输入要用原生 `value` setter 绕过其value tracker，否则事件不触发）。

   现有的 `insertAppleNote()`、`insertStarbucksNote()` 和 `insertAllCustomCards()`
   都是这个模式，改动时留意。

   ⚠️ **平行实现必须一起改（2026-10-22）**：苹果补充说明与星巴克「消费入座」公告
   是同一套机制的两个平行实例（`insertStarbucksNote` 逐条照搬 `insertAppleNote`
   的判据）。只改一段会造成「同一页面两种行为」，且后来者看不出来 ——
   `verify.mjs` §20i 用镜像断言盯着两段结构（标识符与判据写法），漂移即判红。
   另注意 `scripts/check-inject-idempotent.mjs` 按**花括号配对**切函数体
   （早期按「下一个 function 声明」切，新增平行函数后直接把两个函数体粘在一起、
   eval 语法错误）—— 往这两个函数后面再加新函数时，别再改回脆弱定位方式。

### 设计行为（不是 bug）：首屏全屏加载遮罩 + 转圈

**现象**：打开首页时，先看到一整屏不透明白色、居中一个转圈 + 文字「页面加载中…」，约 1–2 秒（快慢取决于 `assets/index-YthXZ9eP.js?v=50` 这个大包下完的时长）后，遮罩消失、完整应用出现。

**这是预期行为，不要把它当 bug 去「修」**：本站是 client-render（React `createRoot`），bundle 体积大，下载+解析期间若直接露馅，会让「全站证据链公示」等 `#root` 之外的静态区块先闪到首屏（即 2026-11-01 站长实测的 FOUC）。遮罩 `#sxg-loading` 位于 `<body>` 开头、`z-index` 最高、不透明白，加载期盖住整页（含顶部公告栏与证据链区块）；React 挂载后由内联轮询脚本移除（每 50ms 检测 `#root` 是否被替换，命中即移除，带 10s 兜底超时防 JS 失败卡死）。`#root` 内占位仅作无 JS 兜底。

**改动历史**：2026-11-01 先试过「`#root` 内加载占位」方案（提交 `e9f5ac0`）——站长实测仍闪（证据链区块在 `#root` 之外，占位盖不住）；同轮改为全屏遮罩（提交 `ca414e9`）根治。完整改动见 [CHANGELOG.md](./CHANGELOG.md)。

**别动它**：删除遮罩或退回「`#root` 内占位」会让 FOUC 复发。若想让转圈更短，给 bundle 加 `<link rel="preload">` 提前拉取即可，不要改结构。

## 🤖 用 AI 查事实：三条铁律

本站 60 张卡的「真实双休率 / 平均下班」全靠证据链撑着，**一条编造的数据会让整张卡失真**。
用 AI 查事实时（核实企业工时、查证报道、补数据），守住这三条：

| # | 铁律 | 为什么 |
|---|---|---|
| 1 | **让它给出处** | 没有出处等于没有事实。要具体的判决号、报道链接、公示文件与日期；「据公开资料」「有研究显示」这类一律不算出处 |
| 2 | **允许它说「不知道」** | 一个从不说不知道的 AI 是在编。提问时直接说「查不到就说查不到，不要推测」，比逼它给答案安全得多 |
| 3 | **关键信息自己再核对** | 出处链接要亲自打开一次。AI 会说错标题、日期和数字，也会编出看着很像真的 URL |

> **落到本站的硬要求**：数据核实结论写进 `员工实测数据核实修改清单.md` 时，
> 必须带可追溯的证据 id 与出处链接。**只有「AI 说」而没有出处的，一律按未核实处理（评级 U）**。
> 宁可标「未核实」，也不能让一个编造的数字挂上「实测」的名义。

> 这三条同样适用于**让 AI 改代码**：它报「已修复」不等于真修好了。
> 本站踩过最贵的坑全是「校验全绿、页面是错的」——改完必须肉眼看过实际渲染结果再上线。

### ⛔ AI 协助开发硬规则（2026-11-03 站长明确，禁止再犯）

本站部分功能由 AI 协助开发。以下规则是**硬性约束**，AI 在任何情况下不得违反：

1. **禁止编造数据**：所有数据必须来自站长提供的原始信息或可溯源的公开证据。
   AI **不得从其他品牌的规则/数据套用到目标品牌**。
   典型案例：AI 曾将 MEMORY.md 中银行评级规则的「轮休做五休二≈8.6 天」直接套用到联通，
   写入详情页与首页卡片。站长纠正：联通实际数据为「月休 6-8 天，仅核实一个城市」。
   **每个品牌的数据独立取值，不存在「通用公式可以套」这回事。**
2. **禁止擅自定级**：新增卡片时，AI 不得看到「招聘信息与实际不符」等描述就一律定 C 级。
   必须先检查站内是否已有同类先例（PITFALLS 21.4：对照先例定级），有先例则对齐先例档位，
   无先例则报告站长、由站长拍板，**不得自行按最保守档处理**。
3. **禁止冒充站长口径**：任何「按站长口径」的表述，必须有 conversation_search 或日志取证
   拿到站长原话作为依据。拿不到就写「AI 拟定，待站长确认」，**绝不允许把自己推断的结论
   说成是站长拍板**。
4. **数据不确定时，问站长**：宁可多问一句、等站长回复，也不许自己编一个数字填上去。
   「查不到写 null / —」是本站的一贯原则，空着比填错强一万倍。

> **违反以上任何一条 = 重大事故**。本站数据的可信度建立在「每条数据可溯源」之上，
> 一条编造的数据会毁掉整张卡、甚至整个站点的公信力。

### U 级硬规则（允许，但规则写死，不是给 AI 偷懒的理由）

U 级 = **证据缺失级**：仅当已尽合理检索（招聘平台 / 媒体报道 / 司法文书 / 官方通报 / 企业信用平台）仍无任何可采信公开证据、且非因企业主动隐匿时使用。它允许存在，但以下规则**由 `scripts/verify.mjs` §2d 机器强制**，任何一条不满足即判红、CI 阻断推送：

1. **必须附「证据缺失说明」**：标 U 的企业详情页 MUST 含证据缺失说明区块（标记 `id="evidence-gap"` 或 `data-evgap="1"`），写明检索了哪些渠道、为何无任何可采信证据；**无说明 = 无效 U = 判红**（堵死「懒得查就标 U」）。
2. **不得自相矛盾**：U 级详情页 MUST NOT 出现「判 S/A/B/C 级」「定级 X 级」这类定档结论——徽标说 U、正文说 C，是最典型的自相矛盾（2026-11-02 三星卡就被站长抓了现行）。注意这**不是**「不能有任何证据条目」：U 页恰恰要记录「查过什么」（规则①的说明块），那些证据只能证明形态、换算不出月休天数，不足以定档。原判据「有证据来源条目就判红」已于 2026-11-02 废弃——它会把「查过但定不了档」的正常 U 页一律误杀。

### 📊 卡面上的「0%」和「—」分别是什么意思

**卡面双休率只有三种形态，没有第四种：**

| 显示 | 含义 | 举例 |
|---|---|---|
| 具体百分比 | 由**排班制度口径换算**得出：官方/招聘/媒体给出「做几休几」，按定义折算 | 做六休一、月休 2 天 → **0%**（每周能休满两天的员工占比为零，按制度必然如此）；大小周 → 约 50% 量级 |
| **0%（口径换算）** | 同上，制度上不存在双休，但特意标注「这不是员工抽样」 | 喜茶、宁德时代、长城汽车（产线口径）、名创优品（门店口径）——2026-10-20 首页实测 4 张 |
| **「—」（未核实）** | 官方与公开渠道**查不到分岗位的月休数据**。本站规矩：**不以估算值填充**——宁可空着，不编一个好看的数字 | 美的（只有「六条禁令」，无双休承诺口径）、大疆、名创优品 |

**为什么 0% 不等于「没查到」**：0% 是换算结论——制度写明做六休一，双休率按定义就是 0，这不是估算，是算术。它与「未核实」的区别是：0% 背后挂着可追溯的招聘页/媒体报道证据 id（rateSource: derived + 证据编号），「—」背后是**查过但查不到**（每张卡的 `rateNote` 里写了查了什么、为什么查不到）。

**为什么「—」不填数**：员工的「每周双休占比」从来不是企业会公示的指标。拿「行业大概这样」去填一个百分比，看起来完整，实际是编数据——这会毁掉本站唯一比数字更值钱的东西：**每一条数据都能溯源**。所以宁可空着。

**想补齐某张卡？** 途径只有一个：提供**可溯源的一手证据**（招聘 JD 截图、排班表、劳动合同相关条款、有据可查的媒体报道），提交 [Issues](https://github.com/dujeongil-galaxy/shuangxiugou/issues/new)。证据够硬，卡面当场从「—」变数字。
