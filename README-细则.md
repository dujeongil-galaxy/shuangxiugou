## 1. React 渲染 DOM 补丁（原「六件最容易踩坑的事」第 6 条）

6. **往 React 渲染的 DOM 里手动插节点，必须假设它会被移位**：

   本站是「React 渲染后用 `index.html` 里的脚本抓 DOM 再改写」的事后打补丁架构。
   **React 重渲染时按位置复用 DOM 节点** —— 卡片被搜索过滤掉后，React 会把那个节点
   原地改写成另一张卡（只更新文本，不重建节点）。而你手动插入的额外子节点
   **React 不认识，文本更新不会清掉它**。

   真实故障：搜索框输入 `HU`，苹果卡消失，但苹果专属的「富士康补充说明」
   留在了华为卡里（`PITFALLS.md` 1.10）；以及搜索无匹配词（如「啊」）时，
   说明框孤零零挂在空搜索面板里（同节 1.10 第二变体）。

   ⚠️ **反向的坑（2026-10-22 修复）**：修 bug ③ 时加的「搜索框一有输入就无条件
   摘除说明框」这条闸，把「说明框只属浏览态」当成了硬规则 —— 结果搜索**命中苹果卡**
   的词（如搜「苹果」）时，苹果卡明明在结果列表里，说明框却被摘掉了（站长截图）。
   **判据必须是「目标卡片在不在当前可见列表」，而不是「有没有在搜索」**。
   「过滤态就一律隐藏」和「过滤态就一律显示」同样是错的。

   写这类补丁必须遵守三条：

   ```js
   // ① 先清后插，不能「已存在就跳过」——那样错位后永远无法纠正
   var existing = document.getElementById('my-note');
   if (existing && existing.parentNode) existing.parentNode.removeChild(existing);

   // ② 目标卡片不在当前列表时，直接不插入
   var target = /* 在当前可见卡片里找 */;
   if (!target) return;

   // ③ 目标卡片「在 DOM 但整棵子树被隐藏」时同样摘除
   //   （沿祖先链查 inline display:none，覆盖筛选的隐藏方式），
   //   且同步清理（不等防抖，防残留一帧）——但只在目标卡片确实不可见时清理，
   //   搜索命中目标卡片时必须保留，否则会误伤正常场景。
   ```

   并且**搜索输入 / 品类评级切换后都要重新调用** —— 这两个操作都会改变卡片列表。
   识别目标卡片用**标题**（卡内 h2/h3）而不是全文子串：华为卡的同品类替代
   推荐区也含「Apple (苹果中国)」，全文匹配会把说明框误插进华为卡。

   改完用 `npm run test:apple-note` / `npm run test:starbucks-note` 验收：
   它用无头浏览器跑真实 React 搜索，覆盖「搜中目标卡保留 / 无匹配词摘除 /
   清空复原 / 搜别家不泄漏 / 子树被隐藏时摘除」五类场景
   （测React 受控输入要用原生 `value` setter 绕过其value tracker，否则事件不触发）。

   现有的 `insertAppleNote()`、`insertStarbucksNote()` 和 `insertAllCustomCards()`
   都是这个模式，改动时留意。

   ⚠️ **平行实现必须一起改（2026-10-22）**：苹果补充说明与星巴克「消费入座」公告
   是同一套机制的两个平行实例（`insertStarbucksNote` 逐条照搬 `insertAppleNote`
   的判据）。只改一段会造成「同一页面两种行为」，且后来者看不出来 ——
   `verify.mjs` §20i 用镜像断言盯着两段结构（标识符与判据写法），漂移即判红。
   另注意 `scripts/check-inject-idempotent.mjs` 按**花括号配对**切函数体
   （早期按「下一个 function 声明」切，新增平行函数后直接把两个函数体粘在一起、
   eval 语法错误）—— 往这两个函数后面再加新函数时，别再改回脆弱定位方式。

## 7. 素材链接规则（blob 格式 / 素材不得明文入库）

**除非站长明确表示「明文」，否则站长提供的截图、图片、短视频、附件等素材一律使用 blob 格式，不得把素材原始文件明文提交进 GitHub 仓库。**

参照本仓库 `why-shuangxiugou.html` 的「照片彩蛋」：仓库里只放 `.enc` 密文容器（`scripts/encrypt-photos.mjs` 生成，PBKDF2-SHA256 21 万次 + AES-256-GCM），页面 `<img>` 只写 `data-enc`、不写 `src`，浏览器本地解密成 Blob 后用 `URL.createObjectURL` 生成 `blob:` 地址写进 `img.src`。页面源码与仓库里都没有可直接打开的静态图片地址。**不要再向站长索要「blog 地址」，也不要把素材塞进站内目录用完整 https 链接引用**——站长 2026-11-07 说的是 blob，当时被误听成 blog，据此做过的一轮站内目录迁移已撤销。

范围：这条管的是**站长口述／提供的素材**。品牌 logo 等站点自带的设计素材（`assets/` 下历史存量）不在此列；加密随笔 `notes.html` 的正文里不放素材外链、不引用仓库内素材路径（正文只有密文，素材一律不上传）。**例外（2026-11-16 站长定稿）**：第 11 章的车道示意静态帧按站长明确要求改为 `data:` URI 内联，图片数据随正文一起进 AES 密文，仓库里没有可直接打开的明文图片；两处 GIF 及 `ch11/` 目录已撤。对面站点 `dating-data-factcheck/picks.html` 的两张评论区截图已按此规则用 `.enc` + blob 落地（`shot-vault.js` + `scripts/encrypt-shots.mjs`）。

配套机器强制：`scripts/verify.mjs` §22 检查本规则原文存在、随笔正文不含仓库内／外部素材引用（只拦非 `data:` 的 `img src` 与 `./ch11/`、`./assets/` 等路径）、仓库根与非 `assets/` 目录不得新增明文素材（用 `git ls-files` 只看已跟踪文件）。对面站点 `dating-data-factcheck` 的 `.github/scripts/check_site.py` 另有一份更严的同源检查（含密文容器结构、口令一致性、`createObjectURL` 链路）。规则不能只写在文档里——**改规则、加素材都要同步改断言并做故障注入**，否则等于没记。

## 8. 随笔文风

站长 2026-11-07 指随笔 8.1「语气过于僵硬，且 AI 味严重」。按口述改写成正文时：

- **像人在讲话，不像在写说明。** 短句叙事；不要提纲式开头，不要把同一个澄清换三种说法连说三遍，不要机械对仗式的收尾，也不要反复叮嘱读者别混淆——要澄清，一次就够。口吻参照相邻的 7.1 / 8.2 / 8.3。
- **不要把两件事写进同一句里比较。** 站长 2026-11-07 在 8.1 上标红了「大概」「跟这条帖子不是同一件事」「跟这条动态不是一回事」：各件事分段各说各的就行，别用「不是一回事／不是同一件事」这类显式澄清句反复否认关联（越否认越像有关系），也别「大概＋还是＋记不清」三重模糊叠在一句里。要区分两件事，靠分段和叙事顺序，不靠叮嘱读者。
- **事实点在叙事里自然带出**，别每段都套一层防误解的限定句；改的是措辞和结构，本意一个字不能变。
- 原有纪律不变：可优化语言但不改本意；带攻击性／情绪的话逐字保留且独立成段；记不清的细节照写「记不清／懒得查」，不代查、不编造、不替站长圆口径。
- **机器强制**：`scripts/verify.mjs` ⑩f 只锁事实要点与「三件事各占一段」的结构（不锁死措辞，正常润色不该判红），⑩g 把典型套话、显式比较句和「大概＋年份」列黑名单防回退。规则不能只写进文档——改文风后同样要跑带 `NOTES_KEY` 的全量校验、做故障注入，再用无头 Edge + CDP 走完整解锁链路截图肉眼验收。

改正文固定三步：覆盖 `notes-备份/notes-plaintext-current.md` 并另存时间戳副本 → `encrypt-notes.mjs --key=…` 只替换 `PAYLOAD` 行（页面结构一字不动）→ 带密码跑 verify 全量。

## 10. 分享弹窗平台口径与防误拦截

**平台清单恒定 15 项 + 复制链接**：国内 5（微信 / QQ / 抖音 / 小红书 / 微博）、
海外 10（Discord / Facebook / X / LinkedIn / Reddit / Telegram / KakaoTalk / Line / WhatsApp / Tumblr）。
**清单不做任何条件裁剪**——不按 UA、不按网络环境、不按「哪个平台可用」动态增删，
否则站长打开只看到一半，又会被当成「平台被吃了」。

**图标一律正圆、排布上 5 下 10**（2026-11-14 站长要求分享图标改成正圆、上 5 下 10 的排布，全站一致）：
国内 5 枚一排、海外 10 枚分两排各 5 枚，`grid-template-columns:repeat(5,1fr)` 固定 5 列，
图标 48px（`max-width:420px` 时 44px）`border-radius:50%`；**列数不随 UA / 视口改**，
手机端同样 5 列（只是图标缩到 44px），避免两端排布不一致又要单独解释。

**分享项一律是 `<button data-share="键">`，DOM 上不许出现外链特征**：

| 禁止 | 原因 |
|---|---|
| `<a href="...twitter.com/intent/...">` | 广告/隐私/跟踪防护扩展按 `a[href*="twitter.com/intent"]` 这类特征整块隐藏，平台会「少几个」 |
| `target="_blank"` / `rel="noopener"` 写在平台项上 | 同上，属于典型外链指纹 |
| 把分享 URL 写进 `href` / `data-url` 等任何 DOM 属性 | 特征仍可被扫到；URL 只许活在 JS 闭包的 `shareTargets` 里 |

**点击走 `openExternal()` 三级兜底**：`window.open(url,'_blank')` →
若返回空或窗口立即被关（`!win || win.closed`，说明连新窗口也被拦）→
**复制分享链接 + toast 明说「新窗口被浏览器拦截，分享链接已复制」**。
任何环境都必须让用户拿到链接，**不许出现「点了没反应」**（原 `a href` 被拦后就是这个表现）。

**机器强制**（改这一块必须同步跑）：
- `verify.mjs` §36v：`share-modal.js` 源码内不得出现 `target="_blank"` / `rel="noopener"` /
  `href="` 拼分享 URL 的写法（注释先剥掉再判）；`data-share` 按钮化 + `openExternal` 兜底在位；
  **15 项清单键名齐全（含 `tumblr`）+ 上 5 下 10 的 `repeat(5,1fr)` 布局钉子**；`?v` 与 `index.html` / `sponsor.html` 挂载号一致。
- `test-share-modal.cjs`（jsdom，33 项）：15 项恒渲染、5 列网格与圆形图标、DOM 零外链特征、被拦（`open` 返回 `null` /
  返回 `{closed:true}`）时必复制并明说、复制类文案、打赏页链接剥 `sponsor.html`。
- `cdp-share-modal.cjs`（真浏览器官能，双视口 1440 / 390）：结构（15 项 / 国内 1 排 5 枚 / 海外 2 排各 5 枚 / 每枚正圆）
  + 逐个点击（9 个外链项含 Tumblr）+ 被拦兜底，**允许任一 `ALL_OK=false` 即失败**。

## 14. 用 AI 查事实三条铁律与协助开发硬规则

本站 60 张卡的「真实双休率 / 平均下班」全靠证据链撑着，**一条编造的数据会让整张卡失真**。
用 AI 查事实时（核实企业工时、查证报道、补数据），守住这三条：

| # | 铁律 | 为什么 |
|---|---|---|
| 1 | **让它给出处** | 没有出处等于没有事实。要具体的判决号、报道链接、公示文件与日期；「据公开资料」「有研究显示」这类一律不算出处 |
| 2 | **允许它说「不知道」** | 一个从不说不知道的 AI 是在编。提问时直接说「查不到就说查不到，不要推测」，比逼它给答案安全得多 |
| 3 | **关键信息自己再核对** | 出处链接要亲自打开一次。AI 会说错标题、日期和数字，也会编出看着很像真的 URL |

> **落到本站的硬要求**：数据核实结论写进 `员工实测数据核实修改清单.md` 时，
> 必须带可追溯的证据 id 与出处链接。**只有「AI 说」而没有出处的，一律按未核实处理（评级 U）**。
> 宁可标「未核实」，也不能让一个编造的数字挂上「实测」的名义。

> 这三条同样适用于**让 AI 改代码**：它报「已修复」不等于真修好了。
> 本站踩过最贵的坑全是「校验全绿、页面是错的」——改完必须肉眼看过实际渲染结果再上线。

### ⛔ AI 协助开发硬规则（2026-11-03 站长明确，禁止再犯）

本站部分功能由 AI 协助开发。以下规则是**硬性约束**，AI 在任何情况下不得违反：

1. **禁止编造数据**：所有数据必须来自站长提供的原始信息或可溯源的公开证据。
   AI **不得从其他品牌的规则/数据套用到目标品牌**。
   典型案例：AI 曾将 MEMORY.md 中银行评级规则的「轮休做五休二≈8.6 天」直接套用到联通，
   写入详情页与首页卡片。站长纠正：联通实际数据为「月休 6-8 天，仅核实一个城市」。
   **每个品牌的数据独立取值，不存在「通用公式可以套」这回事。**
2. **禁止擅自定级**：新增卡片时，AI 不得看到「招聘信息与实际不符」等描述就一律定 C 级。
   必须先检查站内是否已有同类先例（PITFALLS 21.4：对照先例定级），有先例则对齐先例档位，
   无先例则报告站长、由站长拍板，**不得自行按最保守档处理**。
3. **禁止冒充站长口径**：任何「按站长口径」的表述，必须有 conversation_search 或日志取证
   拿到站长原话作为依据。拿不到就写「AI 拟定，待站长确认」，**绝不允许把自己推断的结论
   说成是站长拍板**。
4. **数据不确定时，问站长**：宁可多问一句、等站长回复，也不许自己编一个数字填上去。
   「查不到写 null / —」是本站的一贯原则，空着比填错强一万倍。

> **违反以上任何一条 = 重大事故**。本站数据的可信度建立在「每条数据可溯源」之上，
> 一条编造的数据会毁掉整张卡、甚至整个站点的公信力。

## 15. U 级硬规则

U 级 = **证据缺失级**：仅当已尽合理检索（招聘平台 / 媒体报道 / 司法文书 / 官方通报 / 企业信用平台）仍无任何可采信公开证据、且非因企业主动隐匿时使用。它允许存在，但以下规则**由 `scripts/verify.mjs` §2d 机器强制**，任何一条不满足即判红、CI 阻断推送：

1. **必须附「证据缺失说明」**：标 U 的企业详情页 MUST 含证据缺失说明区块（标记 `id="evidence-gap"` 或 `data-evgap="1"`），写明检索了哪些渠道、为何无任何可采信证据；**无说明 = 无效 U = 判红**（堵死「懒得查就标 U」）。
2. **不得自相矛盾**：U 级详情页 MUST NOT 出现「判 S/A/B/C 级」「定级 X 级」这类定档结论——徽标说 U、正文说 C，是最典型的自相矛盾（2026-11-02 三星卡就被站长抓了现行）。注意这**不是**「不能有任何证据条目」：U 页恰恰要记录「查过什么」（规则①的说明块），那些证据只能证明形态、换算不出月休天数，不足以定档。原判据「有证据来源条目就判红」已于 2026-11-02 废弃——它会把「查过但定不了档」的正常 U 页一律误杀。
3. **单独列示、不混入合格统计**：U 不计入红榜/避雷/观察四格，单独以「证据不足 N 家」呈现（首页四格下方一行小字 + 证据公示区独立统计格）。
4. **gen-pinyin 允许 U 映射**：`scripts/gen-pinyin-index.py` 不再因 U 崩溃，但合规性由 verify §2d 兜底。
5. **禁止偷懒**：不得以「我不确定 / 没空查 / 懒得找」为由标 U——每次标 U 必须记录实际检索动作。

> 旧 U 时代死文案（「待核实（未评级）」「U 级待核实」「参考：其他待核实」「待核实 · 无证据不作评级」）仍禁用：新 U 用「U 级 + 证据缺失说明」，不沿用旧措辞。这五条规则源自 2026-10-31 站长口径：U 级允许使用，但规则必须写死，不能成为省事的借口。
>
> **第六条（2026-11-02 新增，机器强制）**：禁止「查不到即视为无双休」的**举证责任倒置**——把「我没查到」当成「确实没有」再判 C。查不到 → U 级；只有「月休不足 6 天／严重超时／通报违约／**被直接询问双休而拒答**」才判 C。verify 全站扫 brand 页，命中即判红。

## 16. 卡面上的 0% 和 — 分别是什么意思

**卡面双休率只有三种形态，没有第四种：**

| 显示 | 含义 | 举例 |
|---|---|---|
| 具体百分比 | 由**排班制度口径换算**得出：官方/招聘/媒体给出「做几休几」，按定义折算 | 做六休一、月休 2 天 → **0%**（每周能休满两天的员工占比为零，按制度必然如此）；大小周 → 约 50% 量级 |
| **0%（口径换算）** | 同上，制度上不存在双休，但特意标注「这不是员工抽样」 | 喜茶、宁德时代、长城汽车（产线口径）、名创优品（门店口径）——2026-10-20 首页实测 4 张 |
| **「—」（未核实）** | 官方与公开渠道**查不到分岗位的月休数据**。本站规矩：**不以估算值填充**——宁可空着，不编一个好看的数字 | 美的（只有「六条禁令」，无双休承诺口径）、大疆、名创优品 |

**为什么 0% 不等于「没查到」**：0% 是换算结论——制度写明做六休一，双休率按定义就是 0，这不是估算，是算术。它与「未核实」的区别是：0% 背后挂着可追溯的招聘页/媒体报道证据 id（rateSource: derived + 证据编号），「—」背后是**查过但查不到**（每张卡的 `rateNote` 里写了查了什么、为什么查不到）。

**为什么「—」不填数**：员工的「每周双休占比」从来不是企业会公示的指标。拿「行业大概这样」去填一个百分比，看起来完整，实际是编数据——这会毁掉本站唯一比数字更值钱的东西：**每一条数据都能溯源**。所以宁可空着。

**想补齐某张卡？** 途径只有一个：提供**可溯源的一手证据**（招聘 JD 截图、排班表、劳动合同相关条款、有据可查的媒体报道），提交 [Issues](https://github.com/dujeongil-galaxy/shuangxiugou/issues/new)。证据够硬，卡面当场从「—」变数字。
